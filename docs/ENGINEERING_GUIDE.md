# MedStudy 后端工程规范

本项目以大型团队常用的可维护、可审查、可测试和可回滚要求组织开发。本文是 MedStudy 自己的工程约定，参考公开 Go 与 CloudWeGo 文档，不代表任何公司的内部规范。

与本文配套的需求来源为 `GO_BACKEND_API.md` 和 `openapi.yaml`；学习顺序见 `GO_BACKEND_LEARNING_PATH.md`，双仓库操作见 `GIT_BRANCH_GUIDE.md`。

## 1. 结对开发分工

- 用户编写业务数据结构、校验、领域服务、HTTP 业务处理和数据库操作。
- 助手负责根据契约编写测试、准备测试数据、运行验证、审查实现和解释新概念。
- 重复的测试准备工作由助手完成；涉及新的业务逻辑和语法时，先解释，再由用户动手。
- 用户要求“检查”时，助手定位原因并说明修改方式；修改业务实现需用户明确授权。
- 助手维护需求、工程规范和学习进度文档，说明每次改动的依据与验证结果。
- 已存在的业务骨架由用户继续完成；后续新增业务骨架也遵循上述分工。

## 2. 架构与目录职责

第一版采用模块化单体，按业务划分包。当前技术选择为标准库 `net/http`、PostgreSQL 和 pgx；引入新框架或服务必须说明实际需求、成本和迁移影响。

逐步形成以下结构，文件与目录随功能实际需要创建：

```text
cmd/api/                       # 进程入口、依赖组装、启动与关闭
cmd/migrate/                   # 数据库迁移命令
internal/httpapi/              # 路由、handler、HTTP DTO、中间件
internal/folder/               # 资料夹业务规则和服务
internal/document/             # 文档业务规则和服务
internal/flashcard/             # 卡片去重、SRS 和复习服务
internal/auth/                 # 认证、会话和授权规则
internal/platform/postgres/    # pgx 仓储实现及数据库适配
migrations/                    # 版本化 SQL
learning/                      # 独立的语言练习
docs/                          # 契约、设计、开发与运维文档
```

纯语言练习已独立放在 `learning/basics/`，包名为 `basics`，运行命令见 [练习说明](../learning/README.md)。后续练习按主题放入 `learning/`，不混入进程入口或业务包。练习测试中的打印输出不计入正式接口的验收；健康检查、资料夹校验、卡片标准化等真实功能测试继续与被测代码放在一起。

请求通常经过：HTTP handler → 业务 service → repository → PostgreSQL。

- handler 负责 HTTP 解码、请求大小限制、认证上下文、状态码和响应格式。
- service 负责业务规则、授权检查和业务操作的编排。
- repository 负责数据库查询、约束错误转换和事务中的持久化操作。
- 业务服务通过小接口使用持久化能力；接口由使用方定义，数据库实现负责适配。
- 业务规则不依赖 HTTP 对象或 pgx 类型；通过构造函数提供依赖。
- 多表操作的事务由应用服务明确编排，事务内使用同一个事务对象。
- JSON DTO 与数据库记录可以分别建模，避免直接把数据库结构暴露给客户端。

纯校验函数可以直接存在于业务包中。service 和 repository 在实际需要状态或 I/O 时建立；层次以职责为依据。

## 3. 文件与错误组织

文件按明确职责命名，使用小写和下划线。以资料夹包为例：

```text
internal/folder/
├── input.go             # 创建、修改等业务输入
├── errors.go            # 本业务的错误定义
├── validation.go        # 输入规则
├── validation_test.go   # 输入规则测试
├── service.go           # 业务编排，实际需要时创建
└── repository.go        # 持久化接口，实际需要时创建
```

这是按功能增长实施的职责划分。当前 `validation.go` 中的输入和错误定义可在下一次结构整理任务中拆分，由用户完成业务文件调整或明确授权助手执行。

- 包级业务错误集中在本业务的 `errors.go`；通用错误在确实出现跨业务共享需求时提取。
- 用 `errors.Is` 判断约定错误，用 `errors.As` 获取携带字段信息的错误。
- 错误描述供人阅读，程序不能靠比较描述文本决定行为。
- HTTP 层把业务错误映射成契约中的状态码、`error.code` 和字段错误。
- 数据库错误和上游错误保留内部原因，对外返回受控的错误信息。
- 密码、token、AI Key 和完整业务正文不进入错误响应或日志。

## 4. 接口与数据规则

- 实现以 Markdown 和 OpenAPI 的共同契约为准；发现冲突先协调文档。
- 已有 HTTP 接口的字段、时间单位和错误 code 不随实现便利而改变。
- 创建资料夹名称按去除前后空白后的 Unicode 字符数校验，类型仅允许 `material`、`exam`。
- 所有持久资源操作在用户范围内执行；repository 查询显式限定 `user_id`。
- 用户输入使用参数化 SQL；唯一约束和外键负责保护持久数据不变量。
- 涉及复习、批量创建和恢复的接口遵循既定幂等与并发要求。
- 将新资源接口接入服务器时，同时实现契约要求的认证、用户隔离和依赖处理。

## 5. 测试与质量门禁

助手先把需求整理成输入、期望输出和失败场景，再编写测试并解释检查范围。用户根据业务规则实现，不为通过某一条测试编写特殊分支。

- 校验测试覆盖正常、非法、空值、边界和 Unicode 输入。
- HTTP 测试经过真实路由，检查状态码、响应头、JSON、方法与路径行为。
- service 测试覆盖依赖失败、权限拒绝和部分操作成功等业务路径。
- 数据库约束、用户隔离和事务使用真实 PostgreSQL 集成测试验证。
- AI 测试使用本地假服务，覆盖超时、错误响应和非法结构化输出。
- 已实现功能保持可通过；教学中的失败测试明确标记为待完成任务，完成后再提交。
- `t.Skip`、缺少断言或仅打印日志的练习不能作为业务完成的依据。

日常小修改：保存时格式化，运行相关包测试。功能完成和提交前执行：

```bash
go vet ./...
go test ./...
```

格式化由编辑器或 `gofmt` 保证。涉及并发、共享状态和关闭流程时执行 `go test -race ./...`；引入依赖后，把漏洞扫描加入发布检查。CI 在对应阶段统一执行格式、vet、测试、适用的集成/竞态检查和构建。

## 6. 提交与发布管理

当前单人学习阶段沿用既定的后端 `main` 开发方式，以小而完整的提交保存已经完成的功能。开始团队协作或首次正式上线前，升级为功能分支 → Pull Request → CI → review → 合入受保护的 `main`。

- 用户已约定：每完成一个需求并通过适用验收，助手检查 diff 和敏感信息、创建相关提交，并 push 一次到后端当前约定分支；不需要用户再次提醒。需求未完成时不提前按已完成交付推送。
- 提交只包含本次相关文件，业务实现、对应测试和必要文档一起交付。
- 不夹带其他未完成改动；推送前确认待推送提交的范围。遇到权限、远端冲突或验证失败时报告具体情况，不使用强制推送绕过检查。
- PR 说明具体行为变化、验证结果及迁移或部署影响。
- PR 合入要求检查通过；远端分支保护与 CI 配置在相应阶段实际建立并验证。
- 发布顺序为本地验证 → staging 验收 → 数据与回滚检查 → 生产发布。
- 发布保留版本标识、数据库备份、上一版镜像和可执行的回滚步骤。
- 前端保持独立仓库；适配和生产切换遵守已有分支与渐进迁移约定。

## 7. 功能完成标准

一个功能的交付应包含可解释的实现、覆盖关键行为的测试、同步的契约及适用的运行说明。涉及持久化、权限、外部依赖或部署时，相应失败路径也需要验证。

当前目标是逐项实施这些规范；本文中的未来目录、CI、分支保护和发布流程不是已完成能力。每完成一个业务任务，记录实际实现与验证状态。
